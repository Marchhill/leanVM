# EIP-8288 mixed recursion

The optional `eip8288-mixed` feature exposes `eip8288_mixed` through `rec_aggregation` and the `leanvm` facade. It extends the pinned Daisugi profile with one self-recursive guest. Each node verifies either raw SPHINCS signatures, one generic CPU proof, or child proofs in that guest; the root contains one CPU proof and three evaluation points for publicly computable fixed polynomials. Application proofs and bytecode are prover witnesses and are absent from the root encoding.

A dependency is exactly 96 bytes: the 32-byte big-endian scheme word, the 32-byte data hash, and the 32-byte verification-key hash. The scheme is `0x10` for SPHINCS and `0x11` for a generic CPU proof, the latter being this guest's leanSTARK profile. A SPHINCS verification key is the key itself, its root then its public parameter. A generic key hash is Keccak-256 of the 30-byte domain tag `ethereum/8288/leanSTARK/vk/v2` followed by one zero byte followed by the 32-byte program commitment: the digest of the native bytecode table that leanVM's Fiat-Shamir seed absorbs. The profile fixes every other verification parameter, so the commitment is the whole key. The published dependency commitment is `deps_hash`. For a list of only `0x10` entries it is EIP-8288's `get_deps_hash`: BLAKE2s-256 over the sorted unique dependencies' 64-byte `data_hash || verification_key_hash` entries, one compression per entry. EIP-8288 still reserves `0x11` until `get_deps_hash` is defined for it; this guest enables it as a deviation: a list with any `0x11` entry commits to `BLAKE2s(get_deps_hash(sphincs) || get_deps_hash(generic) || LEANSTARK_DEPS_DOMAIN)`, where each inner digest covers that scheme's 64-byte entries and the domain is `eip8288/leanstark-deps` zero-padded to 32 bytes. That 96-byte preimage is never a list of 64-byte entries, so no all-SPHINCS list shares it. The guest hints the split between the two runs and checks every entry's scheme word against its run, in the selected list and in every child's list, so a discarded entry is checked too; any other scheme is rejected. Both schemes share the list's dependency bound. A proof does not carry its dependencies: `verify_mixed_deps` checks it against the digest alone, and a recursive child's dependencies are a prover input.

The public CPU statement hashes the actual guest verification seed, dependency commitment, and deferred polynomial claims. Generic proof public inputs use two canonical 128-bit cells covering all 256 data bits. A generic proof is an EIP-8288 batch leaf: its public input is `get_batch_hash(claims) = Keccak-256(b'EIP8288:batch:v1' || claims)` over 1 to `MAX_CLAIMS_PER_BATCH_LEAF` strictly increasing 32-byte claims, and each claim yields one `0x11` dependency under the program's key. The guest bounds the count before hashing, decomposes each claim into checked bytes, enforces strictly increasing byte-lexicographic order by comparing neighbouring claims byte by byte through their table-checked powers (the leaf verifier need not), hashes the preimage with the Keccak builtin and covers each claim like any other origin. A direct proof of one `data_hash` is the singleton leaf `[data_hash]`. `MAX_CLAIMS_PER_BATCH_LEAF` (16 here; TBD in the EIP) is a guest constant, so changing it changes the key. The guest decodes range-checked canonical instructions into the exact native program table, hashes that table into the program commitment, derives both the key hash and the generic verifier seed from it, verifies the CPU proof, and discharges its program-table evaluation against that reconstructed table. The serialized code is not hashed. Only then may its program evaluation be normalized to a fixed zero evaluation of the mixed guest table. Native code must not substitute a seed-only check for this opening check.

Every selected dependency must have one authenticated origin. Each retained origin writes a distinct running-count marker into a bounded selected slot. Write-once memory prevents two writers from covering one slot, and the constrained terminal count equals the number of selected dependencies. Other authenticated occurrences and discarded dependencies are still verified. Reading an uninitialized coverage flag is insufficient because CPU memory is committed rather than implicitly zero-initialized.

Child CPU proofs verify under the same compiled guest and carry their complete dependency commitment and deferred polynomial statement. A sumcheck batch combines child and generic fixed-matrix evaluations. The final verifier recomputes the mixed guest program and both fixed circuit matrix evaluations at the published points, completing all deferred claims. The encoding is fixed-integer bincode of `(Vec<F192>, [Vec<F192>; 2], cpu::Proof)`. Decode performs bounded count preflight before allocation and reconstructs fixed-polynomial values; callers must separately call `verify()`.

Opening implementations cover the native PCS minimum of 15 through 30. The active profile restricts generic commitments to log 22 and mixed commitments to log 27, with generic bus depths at most 22 and mixed bus depths at most 26. It permits at most 256 dependencies and generic programs of at most 2048 instructions, counting the compiled program padded to a power of two, support code included. Every generic leaf passes these bounds, natively and in the guest, even when all its claims are discarded. A node accepts at most four raw SPHINCS claims, or any mix of up to `MAX_INNER_PROOFS_PER_STEP` (16) batch leaves and recursive children, and rejects more; raw SPHINCS claims use a node of their own. Direct leanSTARK proofs are singleton leaves. Within the log-27 committed bound a node fits at most one leaf with two children, or seven children: a leaf's key-binding kernel and generic verifier dominate. The guest supports 16 structurally, but this profile cannot prove every 16-input mix; raising the bound changes the key and roughly doubles prover memory per log. The 256-dependency list bound is below EIP-8288's `MAX_RLP_BLOCK_SIZE // 96`; longer lists are rejected, never truncated. Combining both schemes uses a mixed recursive parent. This changes which native opening sizes the recursive verifier implements; it does not change the native PCS parameters. The active inverse-rate log is one for generic inputs, mixed outputs, and recursive children. Root proofs and generic inputs must pass the same stream and layout compatibility predicate before acceptance or emission. Program length and resource support are profile choices and must agree between the compiled guest, native acceptance predicate, and application adapter. Structural support for a class does not establish a RAM or latency bound.

The compiler addition is a raw Keccak-f permutation builtin. It reuses the existing SHA3 opcode while canceling that opcode's implicit terminal lane bit and retains its canonical packed-lane constraints. Existing callers and the original Ethereum aggregation guest keep their original behavior when the feature is disabled.

Focused genuine recursion tests are explicitly ignored because they compile and prove the fixed guest. Run them in release mode with an explicit worker count. Tests include same-key depth-two recursion, overlapping parents, discards, full-width public inputs, and malicious hint mutations after the honest public statement has been computed. The resource probe reports compile, preparation, proving and verification durations separately; an external fresh-process measurement is required for peak RSS.

The generic key-binding kernel decodes the complete canonical code and hashes the native program table inside the guest. The feature and its compiler primitive remain separable from the original aggregation API.
