# EIP-8288 mixed recursion

The optional `eip8288-mixed` feature exposes `eip8288_mixed` through `rec_aggregation` and the `leanvm` facade. It extends the pinned Daisugi profile with one self-recursive guest. Each node verifies either raw SPHINCS signatures, one generic CPU proof, or child proofs in that guest; the root contains one CPU proof and three evaluation points for publicly computable fixed polynomials. Application proofs and bytecode are prover witnesses and are absent from the root encoding.

A dependency is exactly 96 bytes: the 32-byte big-endian scheme word, the 32-byte data hash, and the 32-byte verification-key hash. The scheme is `0x10` for SPHINCS and `0x11` for a generic CPU proof. A SPHINCS verification key is the key itself, its root then its public parameter. A generic key hash is Keccak-256 of the canonical program encoding. The published dependency commitment is `deps_hash`, EIP-8288's `get_deps_hash`: BLAKE2s-256 over the sorted unique dependencies' 64-byte `data_hash || verification_key_hash` entries, one compression per entry. EIP-8288 leaves `get_deps_hash` undefined for `0x11`; a list with generic entries commits to `BLAKE2s(get_deps_hash(sphincs) || get_deps_hash(generic) || LEANSTARK_DEPS_DOMAIN)`, a 96-byte preimage no all-SPHINCS list shares. The guest hints the split between the two runs and checks every entry's scheme against its run. A proof does not carry its dependencies: `verify_mixed_deps` checks it against the digest alone, and a recursive child's dependencies are a prover input.

The public CPU statement hashes the actual guest verification seed, dependency commitment, and deferred polynomial claims. Generic proof public inputs use two canonical 128-bit cells covering all 256 data bits. The guest derives the generic verifier seed from the constrained canonical instructions and exact native program table, verifies the CPU proof, and discharges its program-table evaluation against that reconstructed table. Only then may its program evaluation be normalized to a fixed zero evaluation of the mixed guest table. Native code must not substitute a seed-only check for this opening check.

Every selected dependency must have one authenticated origin. Each retained origin writes a distinct running-count marker into a bounded selected slot. Write-once memory prevents two writers from covering one slot, and the constrained terminal count equals the number of selected dependencies. Other authenticated occurrences and discarded dependencies are still verified. Reading an uninitialized coverage flag is insufficient because CPU memory is committed rather than implicitly zero-initialized.

Child CPU proofs verify under the same compiled guest and carry their complete dependency commitment and deferred polynomial statement. A sumcheck batch combines child and generic fixed-matrix evaluations. The final verifier recomputes the mixed guest program and both fixed circuit matrix evaluations at the published points, completing all deferred claims. The encoding is fixed-integer bincode of `(Vec<F192>, [Vec<F192>; 2], cpu::Proof)`. Decode performs bounded count preflight before allocation and reconstructs fixed-polynomial values; callers must separately call `verify()`.

Opening implementations cover the native PCS minimum of 15 through 30. The active profile restricts generic commitments to log 22 and mixed commitments to log 27, with generic bus depths at most 22 and mixed bus depths at most 26. It permits at most 256 dependencies and generic programs of at most 2048 instructions. A node accepts at most four raw SPHINCS claims, one raw generic proof, or two recursive children; these input modes are disjoint. Combining both schemes uses a mixed recursive parent. This changes which native opening sizes the recursive verifier implements; it does not change the native PCS parameters. The active inverse-rate log is one for generic inputs, mixed outputs, and recursive children. Root proofs and generic inputs must pass the same stream and layout compatibility predicate before acceptance or emission. Program length and resource support are profile choices and must agree between the compiled guest, native acceptance predicate, and application adapter. Structural support for a class does not establish a RAM or latency bound.

The compiler addition is a raw Keccak-f permutation builtin. It reuses the existing SHA3 opcode while canceling that opcode's implicit terminal lane bit and retains its canonical packed-lane constraints. Existing callers and the original Ethereum aggregation guest keep their original behavior when the feature is disabled.

Focused genuine recursion tests are explicitly ignored because they compile and prove the fixed guest. Run them in release mode with an explicit worker count. Tests include same-key depth-two recursion, overlapping parents, discards, full-width public inputs, and malicious hint mutations after the honest public statement has been computed. The resource probe reports compile, preparation, proving and verification durations separately; an external fresh-process measurement is required for peak RSS.

The generic key-binding kernel processes the complete canonical code and native program table inside the guest. Host-side code-hash caching does not remove this proof work. A future upstream authenticated program commitment and polynomial opening could replace this kernel through the existing `GenericInput` interface; that would require an explicit key/profile transition rather than silently changing current key semantics. The feature and its compiler primitive remain separable from the original aggregation API.
